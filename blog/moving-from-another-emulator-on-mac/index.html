Move from BlueStacks, MuMu, or Android Studio to SiliconPlay

By Ryan Gibo · Updated 12 November 2026

Moving to SiliconPlay is mostly a reinstall, not a migration. The other app’s virtual disk is not a file I can mount, and I am not going to pretend a “import your BlueStacks data” button exists in version 1.0.0. What you can bring is the APK you still have, the Google account you can sign in with, and the muscle memory for where the buttons were. What you cannot bring is the other emulator’s system image, its keymap files, or a promise that a game’s local save is sitting in a folder I know the path of.

I built SiliconPlay because the emulators I was using did not do what I needed. Some of them were close and then kept the useful part behind a paid plan. The app is free. It runs only on Apple silicon, M1 through M6, including Pro, Max, and Ultra. It is not compatible with Intel Macs. I have tested it on macOS Tahoe and macOS 27 Golden Gate. If you are coming from a Windows emulator article, stop there: this is a Mac app for those chips, not a port of a Windows player.

What stays behind

  • The other app’s virtual disk. SiliconPlay boots the Android 16 image it downloaded, or the SDK you point it at. It does not open another product’s disk image.
  • That product’s keymaps. A preset made for a different mapper does not drop onto SiliconPlay’s buttons. You accept a layout here, or you edit one. The generic preset is MMORPG (WASD).
  • A shared folder you set up in the other app. This guest does not mount a host directory as a live disk. Files you copy with adb go to /sdcard/SiliconPlay.
  • Local saves that lived only inside the old virtual disk, unless the game also saved to a cloud account. I cannot see which of your games do that. Sign in and check before you delete the old app.
  • Split APK sets and XAPK archives you were installing over there. Version 1.0.0 does not install those formats.

A sane order

  1. Leave the old emulator installed until the game you care about is running here. Deleting it first is how you discover the save was local.
  2. Install SiliconPlay from the DMG, drag it to Applications, and let the first run download Android. The license click is Google’s Android SDK license. The download is command-line tools, the Apple silicon emulator, platform-tools, and the Play arm64 image. Details are in the first-run guide.
  3. If Android Studio, or a previous command-line SDK, already has emulator, adb, and sdkmanager, point SiliconPlay at that folder instead of downloading a second copy. A folder that only holds another commercial emulator’s private files is not that SDK. Do not point at it and hope.
  4. On the Play tablet, open Play Store and sign in. Install the game from Play if it is listed. That build is the one Play thinks matches an ARM64 device, which is what this tablet is.
  5. If you must sideload, use a single APK. Cmd+I is the shortcut. Drag and drop works on a running instance. The package still needs an ARM64 library.
  6. Click the Android image. Stay on direct touch until you know the game renders. Then accept a keymap and move the buttons. Do this per game. There is no import of the other app’s control scheme.
  7. Only then uninstall the old emulator, after you have opened the game and seen the account or the save you expected.

From a gaming player

BlueStacks Air and MuMu Player are gaming-oriented apps that also run on Apple silicon. I am not going to recap their licensing here. Check those vendors for how they license their own apps. What matters for the move is the data, not the brand.

If you liked their preset for a specific game, you will not find that preset as a file you can drop on SiliconPlay. Apply MMORPG (WASD), then drag the on-screen buttons until they cover the touch controls. Attack is J, held, in that default. Skills are 1 through 6. A controller uses the same buttons rather than a second map. The editing steps live in keyboard mapping and the genre notes are in layouts for different games.

Multiple instances are a place people get stuck. If the old app let you run two games at once, SiliconPlay can run more than one instance, and it can sync input across them. The Play image and a rooted image are still different tablets. Do not “migrate” by copying a second game onto a rooted APIs tablet and then looking for Play.

From Android Studio

Studio’s emulator is the same family of emulator. That is why an existing SDK folder can be reused when it actually contains the tools. SiliconPlay will still create its own tablet: Android 16, Play image, 1920×1080, landscape, auto-rotate off. It does not adopt a phone-shaped AVD you made in Studio and rename it. If you need a particular device profile, sensors, or the IDE’s debugger UI, stay in Studio for that job. SiliconPlay is the window I use when I want the guest up without living in the IDE, with on-screen controls if the thing I am running is a game.

Do not run both emulators against confusion. If adb devices lists two lines, you have two guests. Installs go to one of them. Quit the one you are not using, or select the device on purpose. More of that workflow is in SiliconPlay next to Android Studio.

From a general virtual machine

UTM and other general VM apps can boot an Android build you installed yourself. That disk is yours. SiliconPlay will not convert it. Export whatever you need as files, then adb push them to /sdcard/SiliconPlay after the SiliconPlay tablet is running. A game installed inside that VM has to be installed again here, from Play or from a single APK. Graphics are a different path. I am not going to claim your old VM’s settings map onto anything in this app.

Accounts

Sign in fresh on the new tablet. The old emulator’s session does not move. The Mac app never sees the Play password. If a game uses its own account on top of Google, you sign in to that too, inside the game, and you follow that game’s terms. Root is optional and off. I turn it on only when I am doing development that needs adb root, on the APIs image, not to “bring a game across.”

After the old app is gone

Deleting the other emulator does not delete SiliconPlay’s SDK folder, and deleting SiliconPlay does not delete the other app’s files. They are different piles. SiliconPlay’s own files are under ~/Library/Application Support/SiliconPlay. The SDK folder is the one you chose, and it remains until you delete it, because it is Google’s emulator and system image. If disk space was why you switched, read disk space and uninstall before you remove both and then wonder why a folder remains.

FAQ

Can I point SiliconPlay at BlueStacks’ or MuMu’s folder?

Only if that folder is a real Android SDK containing emulator, adb, and sdkmanager. A private app-support directory is not that. Pointing at it will not import your games.

My save is gone. Can you recover the old disk?

No. I do not have your old virtual disk, and SiliconPlay does not read it. If you have not deleted the old app yet, open the game there and see whether the save is cloud-side. If you already deleted it, recovery is whatever backup you had, not a feature in this app.

The controls feel different.

They will, until you place the buttons. Direct touch is the default on purpose. Nothing loads a keymap for you on first run, including a preset the app might offer for a known game. You accept it.

Do I need a paid plan to finish the move?

No. SiliconPlay is free. I am not going to describe anyone else’s license on this page. Check the vendor you are leaving if you still have an account with them.
