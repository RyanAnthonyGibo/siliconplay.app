SiliconPlay settings by Mac chip, from M1 to M6

By Ryan Gibo · Updated 12 November 2026

People ask for “the best settings” for an M1, then an M2, then an M4, as if SiliconPlay shipped a different app for each chip. It does not. The DMG is one app. The tablet it creates is one default. This page is what I am willing to say per chip, and the longer list of things I will not invent a slider for.

I build SiliconPlay. It runs on Apple silicon from M1 through M6, including Pro, Max, and Ultra. It is not compatible with Intel Macs. I have tested it on macOS Tahoe and macOS 27 Golden Gate. If you run another macOS version, the settings below are still the ones I know, and I want to hear how the machine behaved.

What does not change with the chip

First run accepts the Android SDK license and downloads Google’s command-line tools, the Apple silicon emulator, platform-tools, and the Play arm64 system image, unless you point at an SDK that already has emulator, adb, and sdkmanager. The tablet is landscape, 1920×1080, 320 dpi, auto-rotate off, named Android 16 Tablet. Those numbers are the defaults version 1.0.0 creates. They are not a suggestion I tuned on an M4 and forgot to mention for the M1.

Direct touch is the default on every chip. A keymap stays off until you accept it. Optional root stays off. The Play image refuses adb root on an M1 and on an M6. Root is a second instance on the Google APIs image, and that image has no Play Store. None of that is a performance setting. Turning root on will not make a game smoother.

There is no kernel extension to allow on one chip and not another, and no background service. The graphics path is the same sentence on every Mac I support: the app is built on the official Android ARM64 emulator, with the graphics translation libraries rewritten for compatibility and frame rate. Vulkan is drawn by Metal. Shaders compile in safe math mode so foliage renders correctly. I have not shipped a per-chip graphics menu, so this guide will not tell you to flip one.

The only measurement

One machine has published numbers. A MacBook Pro with M3 Max, in a demanding 3D game, reached up to 60 fps, at render resolutions up to 2560×1440, with 7–43 ms from key to game. Results vary by game, Mac, and settings. I have not run that same test as a published table for M1, M2, M3, M4, M5, or M6. A neat grid with invented frame rates would be a lie. I will not write it.

What I will say without pretending it is a benchmark: newer chips in this line have more headroom, and headroom matters most in heavy 3D. An M1 that runs a light game is a supported Mac. An M1 that stutters in a heavy one is still a supported Mac having a heavy game. Lower the game’s own graphics settings before you decide the emulator “does not support” the chip.

Do not read 2560×1440 as the size of the window. That figure is how far that one measured game was pushed. The panel SiliconPlay creates is 1920×1080. A game’s internal resolution and the panel size are different numbers. Changing the Mac’s desktop resolution is not the same thing as the game’s render scale, and I have not published a rule that says you should.

What I actually change, on any chip

  1. Confirm the game is the thing stuttering. If the Android home screen is fine and one title is not, the next edit is inside that title.
  2. Drop the game’s resolution or quality one step. I do this before I touch anything on the Mac.
  3. Leave the keymap unloaded if you are only trying to see whether the game renders. Input mapping does not fix a fill-rate problem, and a pile of on-screen buttons makes it harder to see the picture. Command-Shift-G hides them.
  4. Do not start a second instance “to compare” while you are judging frame rate. A second tablet is a second Android. The app can sync input across running instances. That feature is for playing or testing, not for a clean reading of one game.
  5. Close other heavy work on the Mac if you are on a base chip and you are trying to see the game’s ceiling. I am not going to quote a RAM number for the guest. Version 1.0.0 does not document a memory slider, so I will not invent one and then tell you where it sits on an M2 versus an M4.

If a game is simply too heavy for the machine in front of you, the honest outcome is that you play it at lower settings or you play a lighter game. I am not going to dress that up as a hidden preset called “M1 mode.”

Per chip, without fake numbers

M1, M1 Pro, M1 Max, M1 Ultra

Supported. Same app, same first run, same default tablet. This is the chip with the least headroom in the list, which you will notice first in heavy 3D, not in the launcher. I have not published an M1 frame rate. If you write to me about an M1, name the game and the settings you already lowered. “It lags” with no title is a sentence I cannot use.

M2, M2 Pro, M2 Max, M2 Ultra

Supported. I have not published an M2 frame rate either. Treat it as more headroom than M1 and less than a later Max or Ultra, and then stop, because that sentence is not a measurement. The install path does not change. Cmd+I still installs a single APK into the running instance. A missing ARM64 library still fails here the same way it fails on an M6.

M3, M3 Pro, M3 Max

Supported. The M3 Max MacBook Pro is the one measured machine. Do not paste those 60 fps and 7–43 ms figures onto an M3 or an M3 Pro. Same SoC generation is not the same result. Fans, thermals, the game, and whatever else you had open all sit between a chip name and a frame time.

M4, M4 Pro, M4 Max

Supported. Same defaults. People coming from older “M1 or M4 setup” posts sometimes expect a different shortcut list. There is not one. Cmd+I is first on every chip. The rest of the chords I have verified are in the shortcut list.

M5 and M6, including Pro, Max, and Ultra where those exist

Supported. The app does not grow a new settings page because the badge on the laptop changed. If you are on an M5 or M6 and something in version 1.0.0 behaves differently from an M3 Max, I want that mail. I do not want a screenshot of a frame counter with no context. Tell me the game, the in-game settings, the macOS version, and whether the home screen was fine.

macOS, which is not a chip setting

Tested means I ran the app on macOS Tahoe and on macOS 27 Golden Gate. It does not mean I certified every point release, and it does not mean other versions are forbidden. If another version refuses the download, shows a different JDK message, or will not show the guest, that is a report, not a chip tier. Include the version string from About This Mac. I cannot see your machine.

Settings that are not in the app

  • No per-chip profile to import.
  • No “performance mode” I forgot to document. If it is not in version 1.0.0, it is not a setting.
  • No kernel extension that unlocks frame rate.
  • No host-folder mount that would let a game stream assets off the Mac disk as if it were a phone.
  • Safe math shaders are how the graphics path is built, not a checkbox you turn off when you want “more fps.” I am not going to tell you to disable the thing that makes foliage render correctly.

FAQ

Should I set the Mac display to 1920×1080?

You do not have to. 1920×1080 is the Android panel, not a requirement for the Mac desktop. Match them only if you are trying to look at a 1:1 picture and you know why. I have not measured a fps change from the Mac’s scaled resolutions, so I will not claim one.

Does an Ultra chip get a different system image?

No. Play arm64 is the image. Ultra is more cores, not a different Android.

Will an app with no ARM64 build run on a newer chip?

No. The guest is ARM64 on the whole list. A newer chip does not emulate a missing library. Most current apps include an ARM64 build. The ones that do not fail everywhere.

Where do I change controls, if not in a chip profile?

On the running game. Accept a keymap or stay on direct touch. The practical layouts are in on-screen controls for different games.
