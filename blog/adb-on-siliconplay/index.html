Use adb with SiliconPlay: install, push, and logcat

By Ryan Gibo · Updated 12 November 2026

adb is the Android debug bridge. On a SiliconPlay Mac it is not a second app you go and find. The first run downloads Google’s platform-tools into the SDK folder, and adb is in that package, next to the Apple silicon emulator and the system image. If you pointed SiliconPlay at an SDK you already had, the adb you should use is the one inside that folder, not a random copy left on the PATH from an old install.

I built SiliconPlay on the official Android ARM64 emulator. The Mac app around it, the window, the on-screen controls, and the shortcuts, is mine. adb is still Google’s tool. This page is how I actually use it with version 1.0.0, and where I stop rather than invent a flag the app does not document.

What has to be true before adb can see the tablet

The instance has to be running. A stopped tablet has nothing for adb to talk to. Start it from the main window, wait until the Android home screen is up, and only then reach for the terminal. Command-I has the same requirement. If the instance is stopped, import has nowhere to install.

You also have to be looking at the instance you think you are looking at. SiliconPlay can create more than one. The Play image and a rooted Google APIs image are two tablets, not a checkbox on one tablet. adb follows the instance that is running. If both are up, do not assume the next install landed on the window in front of you. The root versus Play image page is the split. This page assumes you have already picked one.

SiliconPlay is for Apple silicon only, M1 through M6, including Pro, Max, and Ultra. It is not compatible with Intel Macs. I have tested it on macOS Tahoe and macOS 27 Golden Gate. If you are on another macOS version, try it and tell me what adb did. I would rather have the report than a guess.

Where the binary is

The SDK folder is the one you chose on first run, or the one you pointed at because it already contained emulator, adb, and sdkmanager. platform-tools sits inside that folder. A folder of APKs is not an SDK. A folder that only has platform sources is not one either.

I am not going to tell you to copy adb into /usr/local/bin. Call it by path from the SDK you actually handed to SiliconPlay, or cd there and run it. If adb version prints a build you do not recognize, you are on a different install than the tablet. That mistake looks like “adb works, the app does not.” It is the other way around.

The Mac app does not mount a host folder as a live disk. Finder will not show the tablet’s storage as a volume, and a directory you share in some other emulator will not appear inside Android on its own. Files you copy with adb go to /sdcard/SiliconPlay. That path is the one this version uses. I am not documenting a second drop folder.

Install a single APK

For a normal single-file APK, the path I want you to learn first is still inside the app. The shortcut list starts with Cmd+I.

Shortcuts that sit next to an adb session
KeysWhat it does in version 1.0.0
Cmd+IImport an APK and install it into the running Android instance. The app menu draws this as Command-I.
F12, or Command-KSwitch Typing and Game keys, after you are done in the terminal and you click the Android image.
Command-Shift-GShow or hide the on-screen game buttons.

Dropping an .apk on the window does the same install as Cmd+I. Use adb when you are already in a build loop and you do not want the file dialog. adb install on a single APK is the command. Replace an existing package with adb install -r when you are iterating on your own build. I am not adding extra flags for downgrades or test-only installs. If you need those, you already know them, and they are adb’s flags, not a SiliconPlay feature.

This version does not install split APKs or XAPK archives, whether you drag them or hand them to adb as one file. A bundle is not one APK. If the package has no ARM64 build, it will not run on this tablet on any chip from M1 to M6. The failure is the package, not adb being “broken on Apple silicon.” More cases are in APKs that do not install or open.

Push a file, then stop

When the thing you need on the tablet is not an installable package, push it:

adb push your-file /sdcard/SiliconPlay/

That is the destination I will stand behind, because it is the one the app uses for files copied this way. Do not invent a shared-folder mount and then file a bug because Finder is empty. The image does not work that way in version 1.0.0.

Pull is the reverse, and it is ordinary adb. I use it when a game or a test run wrote a log or a screenshot into that folder and I want it on the Mac. I am not going to pretend SiliconPlay has a file browser for this. The terminal is the file browser.

logcat, without a fake UI

Pro Mode, off by default, adds hardware, keymaps, and diagnostics to the main window. It is not a logcat viewer, and I am not going to describe menus it does not have. The log is still adb:

adb logcat

Run that only after the instance is up and this adb is the one from the SDK folder SiliconPlay is using. If the output is silent, the usual reason is that you are attached to nothing, or to a different emulator you left running from Android Studio. Quit the other one, or be explicit with adb’s device selection once adb devices shows you more than one line. I am not publishing a serial number or a port for SiliconPlay. Read what adb devices prints on your Mac. That list is the truth for that moment.

Filter the log to your package when the firehose is useless. A crash that happens before your process starts will not show your tag. Look at the lines around the launch, not at the last line after you have already clicked around for a minute.

A loop I actually use

  1. Start the SiliconPlay instance and leave that window up.
  2. From the SDK’s platform-tools, run adb devices and confirm one device that is the tablet you are watching.
  3. Install with Cmd+I, or with adb install -r on a single APK.
  4. If it does not open, check the package for an ARM64 library before you touch graphics settings.
  5. If it opens and then dies, adb logcat while you reproduce it once.
  6. Click the Android image before you expect the keyboard to hit the game. The terminal still owns the keys until you do.

The JDK stub on macOS is a first-run problem, not an adb problem. If setup stopped because /usr/bin/java is only a stub, the app’s message points at brew install openjdk@17. Install that and run the package step again. adb will not download the system image for you.

What I will not tell you to do

  • I will not give you a root command on the Play image. That image refuses adb root. Root is a second tablet on the Google APIs image, and that image has no Play Store.
  • I will not tell you to patch a game. SiliconPlay does not modify games. Follow the game’s own terms if the account matters to you.
  • I will not invent a wireless-debugging toggle. Version 1.0.0 does not document one, so this page does not have one.
  • I will not quote frame rates for adb. Input latency and fps were measured in a game on one Mac, and they have nothing to do with whether adb devices lists a tablet.

FAQ

Does Cmd+I use adb?

The app installs the APK you import. You do not have to open Terminal for that path. adb is there when you want the same install from a script or a build folder.

Can I use Android Studio’s adb?

Only if SiliconPlay is using that same SDK folder, the one that contains emulator, adb, and sdkmanager. Two SDKs means two adb binaries, and they will confuse you the first time both emulators are running.

Why does adb say unauthorized or show an empty list?

Empty means the instance is not running, or this adb is not the one for that emulator. I have not shipped a separate “authorize this computer” step for version 1.0.0, so I am not going to invent the dialog. Start the tablet, check adb devices with the SDK’s own adb, and only then debug the package.

Where do pushed files show up in the guest?

/sdcard/SiliconPlay. If a file manager in the guest does not show it, look at that path anyway. The Mac will not mount it.
