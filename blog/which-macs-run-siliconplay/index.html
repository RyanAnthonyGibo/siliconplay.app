Which Macs run SiliconPlay, and which macOS version was tested

By Ryan Gibo · 3 November 2026

The support line for SiliconPlay is short on purpose. Mac computers with Apple silicon: M1–M6, including Pro, Max, and Ultra. I have tested it on macOS Tahoe and macOS 27 Golden Gate. If you try another macOS version, tell me how it goes. This page is that line unpacked, so you can tell a real limit from a number I have not published.

The chip list is the product boundary

SiliconPlay runs Android 16 on the Mac’s ARM cores through Apple’s Hypervisor framework. The emulator underneath is the Apple silicon build of Google’s official Android Emulator. That is why the chip list is not a performance hint. It is the set of machines the app is built to run on. A Mac outside that list is not a “slower but fine” case I forgot to time. It is outside the app.

Pro, Max, and Ultra are included because they are the same chips with more CPU and GPU cores, not because I maintain a separate build for each badge. The DMG is one app. First run downloads the Apple silicon emulator and the Play arm64 system image into an SDK folder you choose. The tablet it creates is the same default on each of those Macs: 1920×1080, 320 dpi, landscape, auto-rotate off, named Android 16 Tablet.

Tested on macOS Tahoe and macOS 27 Golden Gate

Tested means I ran it on those two versions and I am willing to talk about them. It does not mean I ran a matrix of every older system and stamped them. If you are on another macOS version, you can still try the app. I want the report more than I want to prohibit the attempt. Use the contact page and say the macOS version, the chip, and what stopped. “It did not work” is not a report I can fix.

Other Mac software in the same comparison has its own version lines, and I will not merge them into this one. Mac.apk, which is a different project, needs macOS 26.4 or later and is an alpha that runs apps without an emulator. That requirement is theirs. Genymotion Desktop on Apple silicon needs Rosetta. That requirement is theirs. SiliconPlay’s tested versions are macOS Tahoe and macOS 27 Golden Gate.

What was measured, and on which Mac

One machine has published numbers. A MacBook Pro with M3 Max, in a demanding 3D game, reached up to 60 fps, at render resolutions up to 2560×1440, with 7–43 ms key-to-game input latency. Results vary by game, Mac, and settings. I have not published the same test on an M1, an M2, an M4, an M5, or an M6. Putting those chips in a table with invented frame rates would be a lie with neat columns. I will not do it.

What I will say, without pretending it is a benchmark: newer chips have more headroom, and headroom matters most in heavy 3D games. If a game stutters, lower its graphics settings inside the game before you decide the Mac is “unsupported.” An app that shipped with no ARM64 build will not run on any chip in the list. The tablet is ARM64. Most current apps include an ARM64 build. The ones that do not fail the same way on an M1 and on an M6.

The 1920×1080 default is the tablet panel, not the M3 Max render figure. Do not read 2560×1440 as the size of the window the app creates. It is how far that one measured game was pushed.

Same app, same first run

The setup does not fork by chip. Download the DMG, drag SiliconPlay to Applications, open it, and let it download Android. The license you accept is the Android SDK license. The download is command-line tools, the Apple silicon emulator, platform-tools, and the Play arm64 image, unless you point at an SDK that already has emulator, adb, and sdkmanager. If setup stops because macOS has no JDK, the app says so and points at brew install openjdk@17. Then you run the package step again. That message is about the JDK stub at /usr/bin/java, not about which M-series chip you bought.

There is no kernel extension to allow on one chip and not another, and no background service. Delete the app and it is gone. The SDK folder remains until you delete it. SiliconPlay’s own files are under ~/Library/Application Support/SiliconPlay.

What “will not run” means in practice

  • A package with no ARM64 build. The install path cannot invent the missing library. See APKs that do not install or open.
  • A split APK or an XAPK. This version does not install those formats, on any Mac.
  • A rooted Play tablet. The Play image refuses adb root on every chip. Root is a second tablet on the Google APIs image. See root and the Play image.
  • A game that needs a preset SiliconPlay does not ship. You can still play it with direct touch, or apply MMORPG (WASD) and move the buttons. The absence of a preset is not a chip problem.

Shortcuts, which also do not change by chip

Version 1.0.0 uses the same chords on every supported Mac. Command-I is first.

Shortcuts in SiliconPlay 1.0.0
KeysAction
Command-IImport an APK and install it into Android.
F12, or Command-KToggle Typing and Game keys.
Command-Shift-GShow or hide the on-screen game-button overlay.
EscapeLeave fullscreen. Outside fullscreen, Android Back while the display is focused.
Shift-EscapeRelease every virtual finger.
F10Switch to direct touch.

Other actions are named in the Shortcuts list without a key string I can quote: start or stop the selected instance, toggle fullscreen, save a screenshot, start or stop screen recording, edit the key map, show or hide the Android buttons, and sync input across running instances. Read the chord in the app. It is drawn by the menu.

How to tell me about a Mac I have not measured

If you want a useful note, include the chip (M1–M6, and which of Pro, Max, or Ultra if it has one), the macOS version, the game or the APK, and whether the failure was first-run download, install, drawing, or input. A screen recording is an action the Shortcuts list names. I still will not guess its chord here. If you can capture one from the menu, it is better than a paragraph.
