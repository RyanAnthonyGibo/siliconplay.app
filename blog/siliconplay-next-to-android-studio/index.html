Use SiliconPlay next to Android Studio without keeping the IDE open

By Ryan Gibo · Updated 12 November 2026

Android Studio and SiliconPlay can sit on the same Mac. They are not substitutes. Studio is the IDE, the device manager, and the official emulator with the full UI around it. SiliconPlay is the Mac app I built so I can boot an Android 16 tablet, install a build, and play or poke at it without keeping that IDE open. Under both, when you point them at the same tools, you are looking at the official Android emulator family. This page is how I keep them from stepping on each other.

SiliconPlay runs on Apple silicon, M1 through M6, including Pro, Max, and Ultra. It is not compatible with Intel Macs. I have tested it on macOS Tahoe and macOS 27 Golden Gate. Studio’s own system requirements are Google’s. I am not going to restate them from memory.

When I open which

  • I open Studio when I am editing the project, reading a stack in the IDE, or I need a device profile Studio already defines.
  • I open SiliconPlay when I want the guest up for a game, for a quick APK check, or for on-screen controls. The keymap, the WASD preset, and Cmd+I are the point of this app. Studio does not grow those because SiliconPlay is installed.
  • I do not keep both emulators running while I am judging a single install. Two guests means adb devices has two lines, and the next install is a coin flip unless I select one.

One SDK folder, on purpose

SiliconPlay’s first run can download command-line tools, the Apple silicon emulator, platform-tools, and the Play arm64 image into a folder you choose. If Studio already put emulator, adb, and sdkmanager on the Mac, point SiliconPlay at that folder and skip the second copy. A folder of project source is not an SDK. A folder that only has an APK output is not one either.

Pointing at Studio’s SDK does not turn Studio’s phone AVD into SiliconPlay’s tablet. SiliconPlay creates its own instance: landscape, 1920×1080, 320 dpi, auto-rotate off, Android 16 Play image, named Android 16 Tablet. Your other AVDs stay in Studio. I am not importing them and I am not going to document a checkbox that would.

The inverse is also true. Installing SiliconPlay does not register a device inside Studio’s device manager. If you want the debugger UI, run the emulator Studio launched. If you want this tablet, launch it from SiliconPlay and use adb from the SDK you pointed at.

The install loop without the IDE

  1. Build in Studio, or with whatever Gradle invocation you already trust. I am not replacing your build system.
  2. Quit Studio’s emulator if it is running, or decide you are installing to that one and not to SiliconPlay. Check adb devices with the adb inside the SDK folder.
  3. Start the SiliconPlay instance and wait for the home screen.
  4. Install the single APK. Cmd+I is first. Dropping the .apk on the window is the same install. adb install -r is the loop when the file is already on disk and you do not want a dialog.
  5. If the package is a bundle, an XAPK, or a split set, this version will not install it. Produce a single APK, or install from Play on the Play image.
  6. Click the Android image before you expect keys to hit the app. The IDE and the terminal steal focus, and that is not a guest bug.

The JDK story is the Mac’s, not a rivalry between the two apps. If SiliconPlay’s setup stops because /usr/bin/java is a stub, the message points at brew install openjdk@17. Studio may already have satisfied its own JDK requirement and left the stub in place for everything else. Follow the message you are looking at.

Root and Play, which Studio users already know as two images

You already know a Play system image refuses the usual root switch. SiliconPlay does not special-case that. The Play tablet will not take adb root. A rooted tablet is a second instance on the Google APIs image, and it does not include Play Store. If your app needs Play services, test it on the Play tablet. If your test needs root, test that part on the APIs tablet. Do not spend an afternoon installing Play APKs onto the rooted image. I will not support that as a configuration. The write-up is root versus the Play image.

Logs and the debugger

SiliconPlay’s Pro Mode shows hardware, keymaps, and diagnostics. It does not replace Studio’s debugger. adb logcat from that SDK’s platform-tools is the log, once adb devices shows the tablet you are watching. I am not documenting a JDWP button inside SiliconPlay. If you need breakpoints, use Studio against an emulator it launched, or attach your own tooling to the device adb already lists. I will not invent the attach dialog.

Games you are testing, not just apps

This is the gap Studio leaves open on purpose. A game that wants a finger can stay on direct touch. A game that you want on WASD gets the MMORPG preset only after you accept it, and then you move the buttons. That work is layouts for different games. None of it syncs back into Studio, and Studio’s extended controls do not become SiliconPlay keymaps.

Screenshot and screen recording exist as named actions in version 1.0.0. The chords are drawn in the app’s Shortcuts list and are not a separate string I can quote, so I will not. Use the menu. For a bug you are sending me, the report page is what to include.

Disk, because two tools love to download the same image

If you let SiliconPlay download a full SDK beside Studio’s SDK, you now have two. That is allowed. It is also how a laptop fills up. Prefer one folder when the tools match. If they do not match, because you need a Studio package SiliconPlay is not using, keep both and remember which adb is on your PATH. Call adb by path from the folder the running emulator belongs to. The cleanup rules are in disk space and uninstall. Deleting SiliconPlay.app does not delete Studio’s SDK. Deleting a shared SDK deletes it for both.

FAQ

Do I have to uninstall Studio?

No. They coexist. Do not run both emulators unless you are ready to pick a device in adb.

Will my Studio AVDs show up in SiliconPlay?

No. SiliconPlay creates the Android 16 tablet described above. Your other virtual devices stay in Studio.

Can I debug a game’s native crash from here?

You can get logcat. The IDE’s debugger is still Studio’s. I am not wrapping it.

The app installs in Studio’s emulator and not here.

Check the ABI and the package shape. This guest is ARM64. Split APKs and XAPK files stop at the door. A single APK with an ARM64 library is the file Cmd+I can install.
