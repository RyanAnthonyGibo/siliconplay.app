Optional root, the Play image, and why they are two tablets

By Ryan Gibo · 3 November 2026

Root in SiliconPlay is optional, and it starts off. That sentence is the whole product decision. A normal Play tablet stays a normal Play tablet. Root is a different tablet, on a different system image, created when you ask for adb root. This page is why those cannot be the same tablet, what you lose when you switch, and how to install a package on either one without mixing the files up.

Leave it off unless you need adb root

If you are installing from Google Play, signing in, and playing, you do not want root. The Play image is the one first run downloads: Android 16, ARM64, Google Play included, landscape tablet at 1920×1080 and 320 dpi, auto-rotate off. Play Store on that image is Google’s store, not a store I bundled. SiliconPlay never sees the password you type there.

The Play image refuses adb root. That is not a setting I hid. Turning root on does not flip a bit inside the Play tablet. A rooted tablet uses the Google APIs image instead. Play Store is not included on that tablet. The APIs image is downloaded the first time you create one. If you need both Play sign-in and root, those are two different tablets, not a switch you can flip on a Play image.

I would rather you keep the Play tablet for the account you care about, and create the APIs tablet when a test actually needs root. SiliconPlay does not modify games. Optional root does not change that. Follow each game’s terms. An account ban is the game’s rule, not something this app can appeal.

What you are creating

The main window, with Pro Mode off, shows Start, Stop, and Create New Instance. Create New Instance is how a second tablet comes into existence. Pro Mode, in the toolbar, the View menu, and Settings, adds hardware, keymaps, and diagnostics. It does not replace Create New Instance, and it is not the root switch.

Name the instances in your own head even if the default name is Android 16 Tablet. One of them has Play. One of them, after you ask for root, is the APIs image and has adb root and no Play Store. Installing a Play-only app on the APIs tablet will not grow a store. Signing into Play on the Play tablet will not grant adb root.

There is no kernel extension and no background service attached to either tablet. Delete the Mac app when you are done and the app is gone. SDK files stay in the SDK folder you picked, including the APIs image you downloaded. SiliconPlay’s own files are under ~/Library/Application Support/SiliconPlay.

Installing on the tablet you meant

Start the instance you mean to install onto. Then use one of these. Command-I is first because it is the shortcut, and because it is easy to fire at the wrong window if two instances are up.

  1. Command-I imports an APK and installs it into the running Android.
  2. Drop an .apk file on that instance.
  3. Use adb. Files copied that way go to /sdcard/SiliconPlay on the device adb is talking to.

Split APKs and XAPK archives are not installed by this version, on either image. The images do not mount a host folder as a live disk. If adb lists more than one device because more than one instance is running, look at which one you started. I am not going to invent an adb serial flag the app’s help text does not document. Start the instance you want, and do not assume a copy landed on both.

What root is for, in this app

Root here means you can use adb root on the APIs tablet. It is the developer case: a test that needs system-level access, not a graphics boost and not a way to modify a game. I have not published a list of extra root tools beyond that. If a guide on another site tells you SiliconPlay ships a particular root utility, it is ahead of what this app documents. Do not follow it.

Everyday gaming stays on the Play image with root off. That is the default for a reason. The keyboard mapping, the Metal graphics path, and Command-I all work on the Play tablet without root. None of them require the APIs image.

Graphics and input do not move when you change images

Both tablets are ARM64 Android running on the Mac’s ARM cores through Apple’s Hypervisor framework. Vulkan is drawn by Metal, with shaders compiled in safe math mode so foliage renders correctly. That path is the Mac app, not a property of the Play package. Switching to the APIs image does not turn it off, and it does not raise the only measurement I have published. On a MacBook Pro with M3 Max, a demanding 3D game reached up to 60 fps at render resolutions up to 2560×1440, with 7–43 ms key-to-game latency. Results vary by game, Mac, and settings. I have not published a separate number for the APIs image, so I will not make one up.

Direct touch stays the default on either tablet. A keymap you edit is a profile in SiliconPlay. Accepting a community preset is still a choice, not an automatic load. The shortcut chords do not change because you created a second instance.

The Shortcuts list also names “sync input across running instances” without a readable key string in version 1.0.0. The action exists as a name. I do not know the chord from the help text, so I will not print one. Open Shortcuts on your copy and read it. Do not assume sync is on. Two tablets do not share taps unless that action says they do.

A clean way to keep both

  1. Finish first run so the Play tablet exists. Sign in there if you need the store. Steps are in the first-run guide.
  2. Leave root off on that tablet.
  3. When a test needs adb root, create the APIs instance and let the image download.
  4. Install the package under test with Command-I onto the instance you started.
  5. Delete the Mac app later if you want it gone. Delete the SDK folder yourself if you also want the images gone.
