First run: how SiliconPlay sets up Android 16 on a Mac

By Ryan Gibo · 3 November 2026

The first launch of SiliconPlay is the step people skip past in a hurry, and it is the step that decides whether the rest of the app makes sense. The DMG does not contain Android. It does not contain Google’s emulator. Opening the app the first time is a request to download those pieces, accept the Android SDK license on this Mac, and create one tablet. This page is that sequence, in the order the app actually does it, with the stops I have seen and the ones the app itself tells you about.

What you need before you open the DMG

SiliconPlay is a Mac app for Apple silicon only. That means a Mac with Apple silicon from M1 through M6, including Pro, Max, and Ultra. I have tested it on macOS Tahoe and macOS 27 Golden Gate. I have not certified other macOS versions. If you are on something else, the honest instruction is to try it and tell me what happened, rather than for me to guess.

You do not need Android Studio open, and you do not need a second Android device. You do need enough disk space for an SDK download: command-line tools, the Apple silicon emulator, platform-tools, and a Play arm64 system image. The app asks you to pick the folder those files land in. If you already keep an Android SDK on this Mac and it has emulator, adb, and sdkmanager, you can point SiliconPlay at that folder instead of downloading a second copy.

A Google account is only required if you want to install from the Play Store after the tablet exists. The first-run download itself is the SDK, not a store login.

Install the Mac app

  1. Download SiliconPlay.dmg.
  2. Open the disk image and drag SiliconPlay to Applications.
  3. Open SiliconPlay from Applications. If macOS asks whether you want to open an app from a downloaded disk image, confirm it. That prompt is macOS, not a SiliconPlay account.

There is no kernel extension to approve and no background service to leave running. When you later delete the app, the Mac app is gone. Files you downloaded into the SDK folder stay there until you delete that folder yourself. SiliconPlay’s own files live under ~/Library/Application Support/SiliconPlay.

What “download Android and start” actually does

The first run asks you to download Android and start. Saying yes does four things that are easy to blur together.

First, it accepts the Android SDK license on this Mac. That license is Google’s, for the SDK components the app is about to fetch. SiliconPlay is not a store and it does not replace that license click.

Second, it downloads Google’s command-line tools, the Apple silicon build of the emulator, platform-tools (that is where adb comes from), and the Play arm64 system image. The image is Android 16 with Google Play, built for ARM64. An app that shipped without an ARM64 build will not run on it. Most current apps include one. I go further on that limit in APKs that do not install or open.

Third, it creates one landscape tablet named Android 16 Tablet and opens that tablet in its own window. The default tablet is 1920×1080 at 320 dpi, landscape, with auto-rotate off, on the Android 16 Play image. I did not pick those numbers as a suggestion. They are the defaults this version creates.

Fourth, it stops. You are looking at an Android home screen in a window, not at a game yet. Google Play shows up because that image includes it. It is not a store I bundled inside the DMG. On the Android home screen, open Play Store and sign in. SiliconPlay never sees that password. The sign-in steps, and what the Mac app does not receive, are in signing in to Google Play.

If setup stops because there is no JDK

macOS ships /usr/bin/java as a stub. Tapping it does not give you a Java compiler. Some SDK package steps need a real JDK. When that is the reason setup stops, the app says so. The message points at:

brew install openjdk@17

Install that, then run the package step again from the app. I am not going to invent a second workaround. If the message on your screen names a different command, follow the message. It is looking at your Mac. This page is looking at version 1.0.0.

Homebrew itself is not part of SiliconPlay. If you do not have it, the app’s message is still the place to start, because that is the failure it knows how to describe. Do not copy a random JDK from a forum into the SDK folder and hope sdkmanager notices.

Pointing at an SDK you already have

If Android Studio, or a previous command-line install, already put emulator, adb, and sdkmanager on this Mac, choose that SDK folder when SiliconPlay asks. The app can use it instead of downloading a second copy. The folder still has to be the one that actually contains those tools. A folder of APKs, or a folder that only has platform sources, is not an SDK the app can start from.

Using an existing SDK does not change the tablet SiliconPlay creates, and it does not turn the Play image into a rooted image. Root is a different tablet, created later, on the Google APIs image, because the Play image refuses adb root. Leave that until you need it. The split is explained in root and the Play image.

After the window is open

The main window, with Pro Mode off, stays on Start, Stop, and Create New Instance. Pro Mode is off until you turn it on. It lives in the toolbar, the View menu, and Settings. Turned on, the main window also shows hardware, keymaps, and diagnostics. You do not need it to play or to install the first app.

Direct touch is the default. The pointer is a finger. Click the Android image if you want the keyboard to go to a keymap later. Nothing about the first run loads a keymap for you. A suggested preset, when a known game is in front, stays off until you accept it.

To put a file on the tablet, start the instance first. Then drop an .apk file, or press Command-I to import an APK and install it. Split APKs and XAPK archives are not installed by this version. You can also install with adb. Files copied that way go to /sdcard/SiliconPlay. The image does not mount a host folder as a live disk, so a directory you share in Finder will not appear inside Android on its own.

What I would check before you call the first run broken

  • The Mac is Apple silicon, M1 through M6 in that line. A machine outside that list is outside what this app is built for.
  • The SDK folder you picked is writable, and the download was allowed to finish. A half-written image will not boot into a tablet named Android 16 Tablet.
  • If the app named a missing JDK, the package step was run again after brew install openjdk@17, not just after reading the message.
  • You are starting the instance before you try to install an APK. Command-I on a stopped instance has nothing to install into.
  • You are not expecting Play Store on a rooted APIs tablet. That combination is two tablets, not a checkbox on the Play image.

The measurement I have published for graphics is separate from first run. On a MacBook Pro with M3 Max, a demanding 3D game reached up to 60 fps at render resolutions up to 2560×1440, with 7–43 ms from key to game. Results vary by game, Mac, and settings. I have not published per-chip numbers, and the first-run tablet being 1920×1080 does not mean every game renders at 1920×1080. The panel size and a game’s internal resolution are different things.

Where to go next

If the tablet is up and you want a game on it, use installing an APK or the Play sign-in page. If the keyboard is hitting the wrong place, read typing, game keys, and direct touch before you rebind anything. The shortcut list, with Command-I first, is the keyboard list taken from version 1.0.0.
